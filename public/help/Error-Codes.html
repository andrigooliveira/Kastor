Technical reference

reWork error codes

What each HTTP code means on this platform, when it shows up, and how to fix it. Covers errors the client sees as a toast, messages in the browser console and codes that show up in the server log.

01How to read errors

All reWork error responses follow the format:

{ "error": "Human-readable message" }

The client shows a red toast with that message when the call fails. In the browser console, the log line shows GET/POST /api/... → NNN where NNN is the HTTP code. On the server, each request is logged as METHOD /path → NNN Xms.

i
Where to see the logs Client: F12 → Console tab. Server: the terminal where node server.js runs (or docker logs in production).

02HTTP code families

Codes are grouped by their first digit:

RangeMeaning
2xxSuccess — the server accepted and processed the request.
3xxRedirect — the client needs to go to another URL. reWork rarely uses it.
4xxClient error — something in the request is wrong (invalid data, no permission, missing). The user/frontend needs to adjust.
5xxServer error — the server knew what to do but failed to do it. Report a bug.

400
Bad Request · Invalid request
Client

The server understood the request, but the content is invalid. It's the most common code in reWork because it covers all form validation on the backend.

Frequent examples

  • "Name is required" — empty string field where it's required
  • "Invalid URL" — webhook with a non-HTTP endpoint
  • "Name too long (max. 60)" — exceeded the length
  • "Invalid date." — due date not in YYYY-MM-DD
  • "Select at least one event" — webhook with no events chosen
  • "Password is required" — vault unlock without filling it in

How to fix

Read the toast message — it always points to the field/rule violated. Fix it and resend.

401
Unauthorized · Not authenticated
Client

Session cookie missing, invalid or expired. The requireAuth middleware returns 401 before processing the route.

What happens on the client

The api() helper detects the 401 and calls forceLogout() — it redirects to the sign-in screen without showing a toast (avoids noise on a page that's just waiting for the cookie).

How to fix

  • Sign in again
  • If it persists, check whether the cookie is being sent (F12 → Application → Cookies)
  • Check the session TTL via the KASTOR_SESSION_DAYS env var (default 30)
403
Forbidden · No permission
Client

Authenticated, but the action isn't allowed for this user. Unlike 401, signing in again doesn't help — the permission is really missing.

Typical cases

  • "Only admins can do this" — admin-only route called by a non-admin
  • "Only moderators or admins can do this" — moderator/admin route called by a member
  • "No access to the team." — trying to read/edit an entity of a workspace the user isn't in
  • "vault_locked" — password vault locked (unlock it first)

How to fix

Ask an admin to raise your access level or to add you to the team. For the vault: unlock with password or biometrics.

404
Not Found
Client

Either the route doesn't exist, or the entity requested by id isn't in the cache/database (it was deleted, or the id is wrong).

Examples

  • "Task not found" — opening an old link after the task was deleted
  • "Client/Project/Workflow not found" — the same for other entities
  • "Unknown credential" — trying to authenticate with a removed WebAuthn credential

How to fix

Confirm the id in the URL. If it came from an old link, the entity may have been moved to the Trash (an admin/moderator can restore it at /trash). Outdated slugs don't cause a 404 — the parser extracts the id from the end of the URL.

409
Conflict
Client

Attempt to create/update an entity that violates uniqueness.

Examples

  • "That username is already taken" — adding a user
  • "That email is already in use by another account." — adding a user
  • "That type already exists" — task type library

How to fix

Choose another value. To bring back a deactivated user with the same name, reactivate them instead of creating them again.

413
Payload Too Large
Client

The request body (JSON, upload) is larger than the limit configured in express.json(). The 413 is fired by Express's middleware before the route runs, so the message comes as plain text (not in the { error: ... } format).

Current limits

RouteLimit
/api/uploads, /api/demands*, /api/demands/:id/comment, /api/me, /api/users*, /api/projects*75 MB
All other routes200 KB
Sanitized comment HTML (within the 75MB)200 KB after cleanup

Besides these, each plan has its own per-file limit (see Organization → Plan).

Typical causes

  • Attachment/avatar above ~50MB (base64 overhead turns it into ~75MB)
  • Too many inline images in a single comment
  • A file above the plan's per-file limit

How to fix

  • Compress the image before sending
  • Reduce the number of inline images in the comment
  • For large files, share a link (Drive, etc.) instead of uploading
!
Sign on the client Since the 413 comes as plain text, the toast may show a generic message like "Error 413". Checking the console (Network tab) confirms it.
415
Unsupported Media Type
Client

Upload with a MIME outside the allowlist. reWork blocks it for security:

Allowed MIMEs

  • image/png, image/jpeg, image/gif, image/webp
  • application/pdf
  • Other common formats (docx, xlsx, txt, zip)

Blocked on purpose

  • text/html, application/xhtml+xml — same-origin XSS
  • image/svg+xml — can carry a <script>
  • application/xml, text/xml — XXE in some viewers

How to fix

Convert the file to one of the accepted formats (e.g. export SVG as PNG, HTML as PDF).

429
Too Many Requests
Client

The rate limit kicked in. reWork uses per-user buckets (falling back to IP when not authenticated) on sensitive routes.

Rate-limited routes

  • Sign-in — a few attempts every few minutes per IP
  • Posting comments — flood protection
  • Sending password resets and codes

How to fix

Wait the time shown in the Retry-After header (the toast shows the seconds). After that, the bucket resets. Clicking again doesn't help — each attempt restarts the timer.

500
Internal Server Error
Server

An unhandled exception happened inside a route. That's a bug — the route should have validated beforehand.

What to do

  • Copy the toast + the URL of the screen where it happened
  • If possible, open the console (F12) and copy the details of the /api/... call
  • Open a ticket under Support with steps to reproduce

Known cases

  • Failed to decrypt a vault entry — the master key was changed without migrating; old entries become unreadable
  • Failed to start WebAuthn registration — inconsistent RP config between begin/finish (the domain changed in the middle)
502
Bad Gateway · External service failed
Server

reWork tried to reach an external service and got an error or a timeout. It's not a reWork problem — it's the endpoint being called.

Where it shows up

  • Webhook test — the Discord/Slack/n8n endpoint returned HTTP ≥ 400 or didn't respond within 10s
  • Google Calendar sync — Google API down or token expired
  • Link title — origin server slow or blocked the fetch

How to fix

Try again in a few minutes. If it persists, check the external service's status. For webhooks, review the URL — it may be malformed or disabled at the destination.

503
Service Unavailable
Server

The server is up but can't serve requests right now. Situations:

  • Postgres unreachable (network, credential, container down)
  • Boot still in progress — migration/seed running
  • Corrupted encrypted storage

How to fix

Wait a few seconds and try again (boot finishes quickly). If it persists for more than 1 min, check the container/process logs for the real error.

14Network errors (no HTTP code)

When the request doesn't even reach the server, the client shows:

!
"No connection to the server. Try again in a moment." The Wi-Fi dropped, the container restarted, DNS failed, or the browser blocked it (firewall/proxy). It's not an HTTP error — the fetch didn't even complete.

Quick diagnosis:

  1. Open another tab: if google.com doesn't load, it's the network
  2. Try reloading: if the bare page doesn't open, it's the server
  3. Check the console (Network): a (failed) status confirms a network failure

15Password Vault errors

The vault has specific codes besides the generic ones:

Code / messageWhat it meansHow to fix
403 vault_locked The vault session expired (15 min of inactivity) or was never unlocked. The client takes you back to the unlock screen automatically. Type your password or use biometrics.
401 Incorrect password Unlock with the wrong password. Doesn't create an audit entry (avoids enumeration). Check the password. If you forgot it, use "I forgot my password" on the sign-in screen.
500 Failed to decrypt… The master key on disk changed; the old ciphertext became garbage. Restore the master key backup. Without it, the affected entries need to be added again.

16Biometrics errors (WebAuthn)

The /api/passwords/webauthn/* endpoints have specific codes besides the standard ones. There are also browser-side errors that don't reach the server:

From the server

  • "Registration session expired" — the challenge has a 5-min TTL. Start the registration again.
  • "Session expired" — the same, for authentication. Reopen the modal.
  • "Registration not verified" / "Invalid signature" — the authenticator's response failed FIDO verification. Usually clock drift or a buggy browser; try another device.
  • "Unknown credential" — the credential was removed between begin and finish (rare).
  • "No credentials registered" — tried to unlock without registering anything first.

From the browser (JavaScript)

  • NotAllowedError — the user canceled the OS prompt, or the operation timed out. The client shows "Canceled".
  • InvalidStateError — this authenticator is already registered (caught by excludeCredentials).
  • NotSupportedError — no authenticator available on the device (no Windows Hello, no Touch ID, no FIDO key).

17Quick glossary

  • Middleware — a layer that runs before the route (auth, body parser, rate limit).
  • Rate limit — a cap of N requests in X seconds per key (user or IP).
  • Payload — the request body (JSON, file).
  • MIME — the declared content type (image/png, application/pdf).
  • RP (Relying Party) — the site that trusts the authenticator. Here, reWork's domain.
  • Challenge — a random value the server sends for the authenticator to sign (prevents replay).
  • Assertion — the signature returned by the authenticator. The server verifies it with the stored public key.
  • Sanitizer — a filter that removes dangerous tags/scripts before accepting HTML (used in comments).
